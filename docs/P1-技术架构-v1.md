# 《起个卦 · 技术架构与评估》 v1.0

技术架构总监 柯桥良 · P1 立项产出
（主理人存档 2026-10-20，验收通过；每日一签固定午时口径已仲裁采纳本案建议）

## 〇、结论摘要

**形态**：单 HTML 文件交付（内联 CSS/JS/SVG），原生 JS、零构建、零框架、零外链、零网络请求。
**核心判断**：本项目的技术难点不在 UI，在**占断引擎的确定性 JS 化**与**对拍验证**。参考引擎 meihua.py 已核对完毕，算法口径清晰、可完整移植，对拍方案已设计（见 §三）。
**体积**：预估灰盒 ~60KB、成品 ~150-250KB，预算门禁 300KB。
**建议推进顺序**：P1.5 灰盒（引擎+求签闭环+月历）→ P2 美术与音效 → P3 部署。

## 一、形态与技术栈

### 1.1 技术栈选型：原生 JS，无构建

| 维度 | 权重 | 原生 JS 无构建 | 轻量构建后内联（Vite/esbuild） |
|---|---|---|---|
| 维护成本（一人团队） | 30% | ★★★★★ 单文件即成品 | ★★ 引入 node_modules、版本锁定、构建失败排查 |
| 与"纯本地单 HTML"约束契合 | 25% | ★★★★★ 天然满足 | ★★★ 交付物满足但开发链多一步 |
| 本项目复杂度适配 | 20% | ★★★★★ 三视图+一个引擎，无需框架 | ★★★ 过度工程 |
| file:// 协议兼容 | 15% | ★★★★★ 内联 script 无 CORS 问题 | ★★★★ 同样可内联，但易误用 ES modules（**file:// 下被 Chrome 阻止**） |
| 调试体验 | 10% | ★★★★ 直接改直接刷新 | ★★★★ source map 需配置 |

**结论：原生 JS，无构建，无框架。** 加权约 4.6 vs 3.1。
关键理由：本应用没有状态复杂度诉求（三个视图、一个状态对象）；引入构建链的唯一收益是模块化，而单文件内用"分区注释"即可达到同等纪律性。

**技术红线（写进实现规范）**：
1. 全部代码在一个 `<script>`（IIFE）内，**不得使用 ES modules**——file:// 协议下 `import` 被 Chrome 拦截，这是本地交付形态的硬约束。
2. 禁用 `toISOString()` / `getUTC*()` 取日期——必须用 `getFullYear/getMonth/getDate/getHours` 本地分量（详见 §七时区）。
3. 禁止任何外链：无 CDN、无字体请求、无图片请求（图片一律 SVG 内联或 data URI）。
4. JS 放 `</body>` 前单段内联，HTML 先渲染、JS 后执行，保证首屏不阻塞。

**单文件可维护性触发线**：预计成品 2500-4000 行。约定固定段落顺序（§一.3）。**若超过 ~5000 行再考虑"开发期多文件 + build.py 文本拼接"**（拼接≠编译，10 行 Python），当前不做——不制造伪需求。

### 1.2 文件大小预算

| 组成 | 灰盒 P1.5 | 成品 P2 |
|---|---|---|
| HTML 结构 | ~5KB | ~8KB |
| CSS | ~5KB | ~15KB |
| 引擎 JS（历法+干支+起卦+排盘+判级） | ~25KB | ~25KB |
| 内容库（签文库+64卦表+取象+化解库） | 占位 ~10KB | ~80-140KB（签数待玩法总监定，按 60-100 支估算） |
| UI/存储 JS | ~15KB | ~25KB |
| SVG 素材 | 0 | ~30KB |
| **合计** | **~60KB** | **~190-250KB** |

### 1.3 手机优先响应式
- 设计基准 375px 宽（iPhone SE 档），最大内容宽 480px 居中，>768px 只做居中放大不做复杂分栏（求签是竖屏单手体验）。
- `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">`，适配刘海屏 `env(safe-area-inset-*)`。
- 触控目标 ≥ 44×44px；摇签按钮为主要交互，尺寸放大。
- 视觉细节全部留给 P2，本阶段只定视口规范与三视图布局骨架。

## 二、工程结构（分层 + 分区 + 职责）

### 分层图

```
┌─────────────────────────────────────┐
│  UI 层（视图渲染 / 交互动画 / 音效触发）│  ← P2 美术总监的地盘，只留接口
├─────────────────────────────────────┤
│  App 层（视图路由 / 状态对象 / 事件绑定）│
├─────────────────────────────────────┤
│  Store 层（localStorage 读写 / 容错降级）│
├─────────────────────────────────────┤
│  Content 层（签文库 / 卦表 / 取象 / 宜忌规则 / 色板）│  ← 内容总监的地盘，纯数据
├─────────────────────────────────────┤
│  Engine 层（历法 / 干支 / 起卦 / 排盘 / 判级 —— 纯函数，无 DOM 无 IO）│
└─────────────────────────────────────┘
```

**铁律：Engine 层为纯函数**——输入日期字符串/问题文本，输出排盘结果对象。不触碰 DOM、不读 Date.now() 之外的任何环境状态、不用 Math.random。这是可对拍、可断言的前提。

### 单文件内分区（固定顺序）

```
index.html
├─ <style>      /* §CSS：变量区(色彩令牌，P2 换肤只动这里) / 布局 / 组件 / 动画 */
├─ <body>
│   ├─ #view-qiu     （求签：问题输入 / 摇签筒 / 出签卡 / 化解区）
│   ├─ #view-huangli （黄历：日干支 / 农历 / 宜忌 / 五行穿衣色板）
│   ├─ #view-yueli   （月历：月网格 / 当日记录详情）
│   └─ <nav>         （底部三 Tab）
└─ <script>     /* IIFE 内分区：
                    §A Engine.calendar  历法（农历↔公历、干支、节气月支近似）
                    §B Engine.meihua    起卦/排盘/体用/旺衰/判级
                    §C Engine.huangli   建除十二神 / 宜忌 / 五行色板
                    §D Content          签文库 / 64卦表 / 取象 / 化解库 / 宜忌词典
                    §E Store            localStorage 封装 + 降级
                    §F App              状态 + hash 路由 + 视图渲染
                    §G UI               事件绑定 / 动画 / 音效触发
                    §H Dev              runConformance() 对拍函数（#dev 查询参数才激活） */
```

### 状态管理与视图切换
- 无路由库。用 **location.hash 路由**（`#/qiu` `#/huangli` `#/yueli`）：约 15 行代码，换来 Android 返回键回到上一视图而不是退出页面——手机端体验刚需，值得做。
- 单一 `state` 对象：`{ view, today:{...当日黄历缓存}, currentDraw:{...本次抽签}, calendarMonth:'2026-09' }`；每次状态变更调用对应视图的 `render()` 重绘。三视图间共享数据极少，无需响应式框架。

## 三、梅花易数引擎 JS 化（核心章节）

### 3.1 参考引擎口径核对结果（已逐段读毕 meihua.py，794 行，selftest 全过）

核对确认的口径（JS 端必须逐条对齐）：

| 口径项 | 参考引擎行为（已验证） |
|---|---|
| 先天八卦数 | 乾1 兑2 离3 震4 巽5 坎6 艮7 坤8；**余数 0 取 8；动爻余 0 取 6** |
| 时间起卦 | 上卦=(年支数+农历月+农历日)%8；下卦=(和+时支数)%8；动爻=总 和%6；农历日为农历日序（初一=1），非公历日 |
| 体用铁律 | **动爻所在之卦为用、另一卦为体**；动爻≤3 → 下卦为用；变卦中体不变用变 |
| 生克判定 | 比和=吉 / 用生体=吉 / 体生用=小凶(耗) / 体克用=中吉(费力) / 用克体=凶 |
| 月令旺衰 | 月支×五行 → 旺相休囚死 五档查表（引擎内有完整表，共 12×5） |
| 日柱锚点 | JDN+49 mod 60；2000-01-01=戊午（selftest 验证含 1949-10-01=甲子） |
| 换日边界 | 默认 **23 点换日**（子时换日，八字惯例），日柱受影响；时柱五鼠遁 |
| 年柱分界 | 以立春≈公历 2/4 硬编码近似（存在 ±1 天误差，属已知口径） |
| 节气月支 | 用 12 节近似日期表（±1 天误差，仅作旺衰辅助） |
| 农历表 | 1900-2100 共 201 项每年 1 个 16bit 码；锚点 1900-01-31=正月初一(JDN 2415051)；**超范围直接抛错** |
| 越界行为 | `solar_to_lunar` 对 <1900 / >2100 抛 ValueError → JS 端对应 return null + UI 降级提示 |

### 3.2 农历数据范围取舍：**选全量 1900-2100**

| 方案 | 数据体积 | 边界防御成本 | 风险 |
|---|---|---|---|
| 全量 1900-2100（201 项） | ~1.2KB（十进制数组） | 0 | 无 |
| 缩窄 2020-2060（41 项） | ~0.25KB | 需额外越界提示逻辑；用户设备时间错乱/翻月历越界即触雷 | 省不到 1KB |

**结论：体积差约 1KB，在一个 200KB 级文件里完全不构成取舍理由，缩窄反而增加边界代码。直接全量。** JS 表示为 `const LUNAR_INFO=[19416,19168,...]` 十进制数组（比 0x 字符串再省 ~20%）。

### 3.3 起卦方式映射到玩法（占位口径，**问事签口径需玩法总监拍板**，见文末开放问题）

| 玩法场景 | 起卦方式 | 确定性 |
|---|---|---|
| 问事签（用户输入问题） | **字数起卦**（经典梅花字占的"字数"变体）：问题总字数 n → 前半字数%8 定上卦、后半字数%8 定下卦、总字数%6 定动爻 | 同一问题永远同一卦（"同问同签"，符合传统"再三渎则不告"）；**签级仍随当日月令旺衰浮动**（同卦不同日可不同签级）——建议默认口径 |
| 每日一签（不输问题） | **时间起卦**：以当日日期+固定午时（或抽签真实时辰，二选一，建议固定午时使"每日一签"全天唯一） | 同一天结果唯一，天然"每日一签" |
| 摇签动画的"随机感" | 表现层动画（签枝跳动）可用 Math.random / 确定性种子 PRNG，**但结果在点击瞬间已由 Engine 算出**，动画只演出结果 | Math.random 被限制在 §G UI 分区内；Engine/结果路径禁用（写入规范，对拍断言覆盖） |

### 3.4 判级映射（机制 + 占位矩阵，内容待玩法总监复核）

签级 = f( 体用生克主卦关系 × 体卦月令旺衰 × 变卦关系修正 )，五关系 × 五旺衰 → 七档签级（上上/上/中上/中/中下/下/下下）。实现为一张 5×5 基础矩阵 + 变卦升降一档的修正规则（变卦关系优于主卦则升、劣则降，用克体不降穿下限）。矩阵内容属内容层（§D），我给出占位矩阵，由 game-design-director 复核吉凶分寸。

### 3.5 对拍方案（引擎一致性验证）

1. **基准生成**：用 `meihua.py --json` 生成基准用例集，存为 JSON 文件（不进交付物，仅开发期资产）：
   - 时间起卦 12 例：2025-2026 逐月取 1 例 + **23 点换日边界 2 例**（22 时/23 时各一）+ 立春边界 2 例（2/3 与 2/5）+ 闰月日期 2 例（2025 闰六月）；
   - 农历↔公历往返：24 个月初一 + 1900/2100 两端点；
   - 数字起卦 8 例：含余 0 边界（输入%8==0、%6==0 各 2 例）；
   - 直给卦 6 例：动爻 1-6 各一，覆盖体用定位全部两种位置；
   - 锚点：2000-01-01=戊午、1949-10-01=甲子（与参考 selftest 同款）。
2. **JS 侧**：`runConformance()` 开发函数（`index.html#dev` 才激活），同输入跑全用例，输出 JSON。
3. **比对**：`node extract.js`（开发期 10 行脚本）从 HTML 抠出引擎段跑 Node，与基准逐字段 diff：本卦上下卦/卦名卦序/动爻/互变错综/体用五行/主变卦关系/月支/日柱/旬空/体用旺衰。**全字段全等**为过。
4. **已知差异点须显式对齐**：节气月支为近似口径——对拍时统一用 `--month-branch` 显式指定月支跑主对拍，再单独跑 4 例近似路径验证近似表逐字节一致；年柱 2/4 硬编码分界同款复刻。
5. **语言差异注意**：Python `%` 与 JS `%` 在**负数**上行为不同——已核对引擎所有取模输入恒为正（年支数/字数/农历日月均≥1），无风险，但对拍脚本中写明此断言前提。
6. **确定性断言**：同输入连跑两遍，JSON 序列化逐字节相等；同一问题文本+同一日期，判级/签诗/化解全链路输出相等。进灰盒验收清单。

## 四、黄历与五行穿衣（纯本地计算，零数据文件）

### 4.1 日干支
Engine 层直接复用对拍过的日柱计算（JDN+49 mod 60，23 点换日）。

### 4.2 宜忌生成：建除十二神规则（确定性，无外部数据）
- **建除十二神**：值 = (日支序 − 月支序) mod 12 → 建/除/满/平/定/执/破/危/成/收/开/闭，十二神各有传统宜忌口诀（如"建宜出行、破宜破屋……"）。
- **内容层词典**（§D）：十二神 × 宜忌词表（每神 3-5 宜 + 2-3 忌），由玩法总监/内容复核定稿；总量 <2KB。
- **冲煞**：日支六冲（子午、丑未……查表）→ "冲X煞X方位"，纯查表。
- 明确不做：完整老黄历（神煞全表、彭祖百忌等）——超出范围，先用十二神+冲煞够支撑"当日黄历"体验。

### 4.3 五行穿衣色板
基准 = 当日**天干五行**（甲乙木/丙丁火/戊己土/庚辛金/壬癸水）。确定性映射规则（通行简化口径）：

| 关系 | 色板定位 |
|---|---|
| 生当日五行者（印） | 大吉色 |
| 与当日五行同类 | 次吉色 |
| 当日五行所克者（财） | 一般/可用 |
| 克当日五行者 | 慎用色 |
| 当日五行所生者（泄） | 不宜色 |

五行→颜色映射（金=白/银/杏、木=绿/青、水=黑/蓝/灰、火=红/紫/粉、土=黄/棕/卡其）。全部查表 <1KB。**此口径通行但有流派差异，标注为内容层占位，请玩法总监确认口径**。

## 五、音效方案（Web Audio 合成，零音频文件）

- **摇签沙沙声**：白噪声 buffer + bandpass 滤波（中心 ~3kHz，Q≈0.8）+ 随动画节奏的增益包络，循环至摇签结束。合成代码 ~40 行。
- **出签声**：短音调（正弦+快速衰减包络，建议取五声音阶宫音 ~262Hz 起，P2 美术总监定调性）+ 一点噪声点缀模拟"竹签落筒"。~20 行。
- **移动端自动播放限制处理（关键）**：iOS/Android 均要求 AudioContext 在**用户手势内**创建或 resume。实现规范：摇签按钮的 `pointerdown` 事件内执行 `ctx = new (AudioContext||webkitAudioContext)(); ctx.resume()`；若 `ctx.state !== 'running'` 则本次静音（下次手势再试）。**任何音效失败都不得打断抽签流程**（try/catch 全包裹）。
- 不做背景音乐（体积+循环合成复杂度不值），P2 可复议。

## 六、localStorage 数据结构

### 6.1 键设计（单键覆盖，遵守硬约束）

```
键名: qigegua.v1        （全应用唯一一个键）
值:   {
        "schema": 1,
        "records": [ {...}, ... ]     // 抽签记录数组，追加后整体覆盖写回
      }
```
- **不拆键**：每日一签状态从 records 按日期查询得出（`records` 内查当日是否有 `type:"daily"` 记录），不另设"最后抽签日"键。
- **SCHEMA_VERSION**：写入 `schema:1` 字段；读取时若 `schema` 缺失/不识别 → 视为损坏，降级为忽略旧数据重新初始化（不 crash）。**只在记录条目形状变更时 bump**（如给记录加字段），并写迁移函数。

### 6.2 记录条目 schema（每条 ~150-250B）

```json
{ "d": "2026-09-17",      // 本地日期 YYYY-MM-DD
  "t": 1726560000000,     // 抽签时刻 epoch ms（用于同日多签排序展示）
  "type": "ask",          // ask=问事签 daily=每日一签
  "q": "换工作顺利吗",     // 问题，≤50字，daily 省略
  "lv": "中下",           // 签级 上上~下下
  "hex": "水山蹇",        // 卦名
  "stick": 23,            // 签支号
  "sum": "遇蹇难行，宜守不宜进",  // 摘要 ≤30字（月历列表用）
  "h": 7                  // 化解建议编号（未化解则省略） }
```

### 6.3 容量评估
一年 365 条 × ~200B ≈ **72KB**（即使重度用户一天 3 条、连续三年也只有 ~650KB），iOS Safari localStorage 限额 ~5MB/origin，**余量 7 倍以上**，无需清理/归档机制。写入方式为"读数组→push→整体 JSON.stringify 覆盖写"，单次写入 <1ms，无性能问题。

### 6.4 数据清空风险与导出取舍（列取舍，不拍板）
风险事实：用户清浏览器数据/卸载浏览器/隐私模式 = 记录丢失，且**本地 file:// 打开时不同路径的文件可能属于不同 origin**（见 §七风险 3）。缓解选项：
- **A. 不做导出**：接受"轻记事"定位，UI 用一句文案管理预期（"记录仅存于本机浏览器"）。成本 0。
- **B. 导出为文本/JSON**：一个"复制记录"或"下载 .txt"按钮，代码 ~2KB，依赖用户主动操作。
- **C. 部署后云备份**：违反零联网零收集硬约束，**直接排除**。
取舍点：A 简单诚实；B 成本极低且能救"换手机/清缓存"场景，但导出的文件含问题文本，用户误分享有隐私面。**交主理人/用户拍板，架构上两案均无障碍（Store 层已把记录读路径封装，导出只是加一个读出口）。**

## 七、性能预算表

| # | 指标 | 数值目标 | 测量方式 | 超阈处置 |
|---|---|---|---|---|
| 1 | **单文件体积**（门禁） | ≤300KB（内容库膨胀预警线 250KB） | 交付门禁：文件属性，每次交付时 team-lead 按此表核对 | **门禁卡点**：卡在每个交付节点，超标退回主程序压缩签文库（减每签字数/砍签数），或经重新评估后书面上调预算 |

## 九、P1.5 灰盒计划（色块版可玩闭环）

**范围**：无美术、无音效、无动画（占位色块+系统字体），验证**引擎正确性 + 求签闭环 + 存取可靠**三件事。

**做什么**：
1. Engine 全量：农历↔公历、干支四柱、时间起卦、字数起卦、互变错综、体用定位与生克、月令旺衰、判级映射（占位矩阵）、建除十二神+宜忌、五行色板；
2. 求签视图：问题输入框（可空）→"摇签"按钮 → 文字版出签（签级/卦名/占位签诗/解签要点/化解按钮）→ 中下以下点化解出占位建议文本；
3. 黄历视图：纯文字（日干支/农历/建除/宜忌/穿衣色块用五色占位）；
4. 月历视图：数字网格 + 当月有记录的日期标记，点开看当日记录详情；
5. Store：单键读写 + schema 字段 + 三类降级路径；
6. hash 路由 + 底部三 Tab（色块样式）。

**不做**：SVG 仙鹤、签筒动画、音效、真签文库（用 10 支占位签）、化解仪式动效、导出。

**灰盒验收口径**（全部可断言，过则 P1.5 完结）：
- [ ] §3.5 对拍：≥30 基准用例全字段通过
- [ ] 确定性：同问题+同日期两跑，输出 JSON 逐字节一致
- [ ] 全流程手测：输入问题→摇签→出签→（中下以下）化解→月历可见该记录→点开详情正确
- [ ] 每日一签：不输问题抽签，同一天内两次结果一致
- [ ] Network 面板 0 请求（file:// 打开，含点击所有按钮后）
- [ ] iPhone SE 视口(375×667)三视图布局不错位、按钮可点
- [ ] Safari 无痕模式：抽签可完成 + 显示"无法保存"提示不崩溃
- [ ] 系统日期改到 2101：显示历法超范围提示，不白屏
- [ ] 体积 ≤100KB（灰盒门禁，比成品严）
- [ ] 打点数据留档：摇签延迟、月历渲染实测值记录进验收单

**交付节奏**：灰盒完成后交用户体验"玩法对不对"，再进 P2 美术——避免在错误的玩法上花美术成本。

## 十、前提假设（假设变更则结论重估）

1. 目标设备为现代手机浏览器（iOS Safari ≥13 / Android Chrome ≥90）；
2. 签文数量在 60-100 支量级（若总监定 300+ 支，内容库体积预算需重估）；
3. 无多语言、无深色模式（P2 美术总监可提，色彩令牌已预留）；
4. 判级矩阵/签文库/宜忌词典的内容生产在内容层完成，引擎只管机制；
5. 平台规则（静态托管服务条款等）以 P3 阶段官方文档为准。
